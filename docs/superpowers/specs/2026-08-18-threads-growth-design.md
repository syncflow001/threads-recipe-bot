# 스레드 성장 자동화 — 설계

2026-08-18 · 갈래 `feat/threads-rebuild`

## 0. 한 줄

스레드에서 바이럴 중인 요리 글을 수집해, 내 말투로 재구성하고, 내 계정에 자동 발행한다.
목적은 **계정을 꾸준히 키우는 것**이다. 수익은 곁다리다.

## 1. 이전 제품과의 관계

`coupas-auto` 는 인스타 릴스마다 쿠팡 SubID를 붙여 **어느 릴스가 얼마 벌었는지 측정**하는
다중 사용자 SaaS 였다. 3차 슬라이스까지 만들어 배포했다.

이번은 **리팩터링이 아니라 다른 제품**이다. 플랫폼(인스타→스레드)·행위(측정→발행)·
목적(수익추적→계정성장)이 전부 바뀐다. 코드 2,250줄 중 이어 쓰는 것은 약 130줄이다.

옛 제품은 지우지 않는다. `archive/2026-08-18-instagram-saas/` 에 원래 경로 그대로 보관하고,
갈래 `feat/beta-readiness` 도 남긴다. 되살릴 때는 반대로 옮기기만 하면 된다.

## 2. 확정 사항

| 항목 | 값 |
|---|---|
| 대상 | 스레드 (Threads) |
| 키워드 | 레시피 · 요리 · 집밥 · 한식 |
| 점수 기준 | **좋아요 ÷ 조회수** |
| 등급 | 플래티넘 · 골드 · 실버 · 브론즈 (구간은 실측 후 확정) |
| 수집 기법 | **인터셉터** — 통신 가로채기 |
| 미디어 | 내려받아 그대로 첨부 |
| 재구성 | LLM. 본문과 레시피로 분할 |

| 저장 | `chrome.storage` |
| 사용자 | 나 혼자. 로그인·다중 사용자 없음 |

## 2-1. 실측 — 무엇을 어떻게 얻는가 (2026-08-18)

Playwright 로 실제 로그인 세션에서 확인했다. **추측이 아니다.** 표본은
`docs/threads-sample-2026-08-18.json` (게시물 76개).

### 가로채기는 필요 없다

처음에는 인터셉터로 갔지만, 확인해 보니 **HTTP 요청 두 종류로 전부 얻어진다.**
페이지에 스크립트를 심을 필요도, 통신을 가로챌 필요도 없다.

핵심은 **요청을 브라우저의 페이지 이동처럼 위장하는 것**이다. 이 헤더가 없으면
껍데기만 오고 데이터가 빠진다.

```js
const 문서요청 = {
  credentials: 'include',
  headers: {
    'Accept': 'text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8',
    'Sec-Fetch-Dest': 'document',   // 이 두 줄이 없으면 데이터가 안 온다
    'Sec-Fetch-Mode': 'navigate',
    'Sec-Fetch-Site': 'none',
    'Upgrade-Insecure-Requests': '1',
  },
}
```

| 요청 | 얻는 것 |
|---|---|
| `GET /search?q={키워드}&serp_type=default` | **게시물 20개** — 좋아요·공유·리포스트·댓글·본문·미디어주소·영상자막·이미지OCR |
| `GET /@{작성자}/post/{code}` | **`impression_count`** (조회수) |

데이터는 인라인 `<script type="application/json">` 안에 있다. 정규식으로 뽑아
`JSON.parse` 한 뒤 `code`·`user.username`·`like_count`·`caption` 을 모두 가진 객체를 찾으면 게시물이다.

조회수만 검색 응답에 없다. 전용 질의 `BarcelonaPostViewCountQuery` 의 프리페치 결과라
상세 문서에만 실린다. 경로는 `data.media.text_post_app_info.impression_count` 다.
게시물당 약 900KB · 2.6초. 6개씩 병렬로 76개를 문제없이 받았다.

`doc_id` 를 알아내 GraphQL 을 직접 부르면 훨씬 가볍지만, 그 값은 JS 번들 안에 있고
배포마다 바뀐다. 지금 방식이 통하는 한 쫓지 않는다.

### 미디어 — 형식은 고를 수 없다

`image_versions2.candidates` 는 한 게시물 안에서 **전부 같은 형식**이다. 게시물에 따라
전부 jpg 이거나 전부 webp 다. `candidates[0]` 이 항상 최대 크기다.

**주소는 서명돼 있다.** 끝의 `oh=` 가 `stp`(형식·크기 지정) 값까지 포함해 서명하므로,
`stp` 를 떼거나 바꾸면 **403** 이다. 실측으로 확인했다.

| 시도 | 결과 |
|---|---|
| 주소 그대로 | 200 · 1080×1350 · 232KB |
| `stp` 제거 | 403 |
| `stp=dst-webp` | 403 |

따라서 받는 쪽에 형식 선택권이 없다. 경쟁사에서 webp 와 jpg 가 섞여 나오는 것도 같은 이유다.
파일 이름은 **주소에 적힌 실제 확장자**를 따라야 한다. 종류로 넘겨짚으면 내용과 어긋난다.

⚠️ **3번 태스크에서 확인할 것** — 스레드 발행 API 가 WebP 를 받는가.
안 받으면 올리기 전에 우리가 변환해야 한다. 형식을 못 고르므로 피할 수 없는 문제다.

### 레시피는 본문이 아니라 글타래에 있다

본문은 "이거 봐봐" 하는 낚시고, **재료와 순서는 작성자가 자기 글에 이어 단 답글에 있다.**
쿠팡 링크도 거기 들어 있다. 본문만 긁으면 재료 한 줄에 순서가 빈 글이 나온다.
상세 요청은 조회수 때문에 어차피 하므로 같은 요청에서 함께 건진다.

작성자는 나중에 댓글마다 답장도 단다. 그것까지 넘기면 "고마워 맛있게 해먹어" 같은 잡담이
레시피에 섞인다. `self_thread_info` 는 항상 `null` 이라 쓸 수 없어서 **시간으로 가른다** —
남이 처음 댓글을 달기 전에 올라온 것만 글타래로 본다.

**영상 자막은 쓸 수 없다.** `transcription_data` · `seo_transcript_for_related_post` ·
`seo_ocr_for_related_post` · `accessibility_caption` 은 전부 스키마에만 있고 값이 없다 —
확인한 게시물 전부, 등장 94회 전부 `null` 이었다. 직접 음성인식을 돌리는 건 배보다 배꼽이라
하지 않는다. 대신 **레시피가 실제로 적힌 글만 후보로 남긴다** (분량 표기 3개 이상).
후보 24개 중 글타래가 있는 것이 15개, 그중 진짜 레시피가 8개였다.

⚠️ **폭 없는 문자를 씻어내야 한다.** 스레드 글에는 제로폭 공백과 이모지 변형 선택자가
게시물당 3~25개씩 섞여 있다. 자바스크립트의 `\s` 는 이것들을 공백으로 치지 않아
`1<제로폭>모` 가 분량으로 안 잡히고, 멀쩡한 레시피가 통째로 걸러진다.

### 쿠파스 링크 — 딥링크는 순수 상품주소만 받는다

실측으로 확인했다.

| 넣은 주소 | 결과 |
|---|---|
| `https://www.coupang.com/vp/products/{id}` | **성공** |
| 같은 주소에 `?itemId=…&vendorItemId=…` | 400 `url convert failed` |
| 상품검색이 돌려준 `productUrl` | 400 — **이미 제휴 링크다** |

그래서 검색 결과에서 `productId` 만 꺼내 순수 주소를 다시 만든다.
발급된 링크를 실제로 따라가 `subid=tDacui_1gT3T` 가 실린 것까지 확인했다.
**글마다 다른 꼬리표가 붙는다는 이 제품의 전제가 끝에서 끝까지 증명된 지점이다.**

어떤 상품을 걸지는 재구성할 때 LLM 이 `추천검색어` 로 고르고, **주소는 코드가 만든다.**
LLM 에게 주소를 맡기면 지어내거나 한 글자 흘려서 수수료가 날아간다.

### 발행 — 실측 (2026-08-18)

실제로 올려 보고 확인했다.

| 확인한 것 | 결과 |
|---|---|
| 본문 + 레시피 답글 구조 | **된다.** 답글은 `reply_to_id` 로 잇는다 |
| 파일을 어딘가에 올려야 하나 | **아니다.** 스레드가 주소를 받아 직접 가져간다 |
| WebP 를 받는가 | **받는다.** 받아서 JPEG 로 알아서 바꿔 저장한다 (60KB → 165KB) |
| 메타 CDN **이미지** 주소 | 통과 |
| 메타 CDN **영상** 주소 | **거부.** `status: ERROR`, 사유 `UNKNOWN` |
| 메타 밖 공개 영상 주소 | 통과 — 영상 발행 기능 자체는 멀쩡하다 |

**메타는 자기 CDN 의 영상 주소를 발행 재료로 받지 않는다.** 같은 파일을 메타 밖 주소로 주면
통과하므로 파일 문제가 아니다 (H.264/AAC·720×764·18.7초·2.4MB 로 규격 안이었다).
이미지는 막지 않는다. 퍼나르기를 막으려는 조치로 보인다.

그래서 지금은 **영상을 빼고 이미지만 올린다.** 영상을 올리려면 내려받은 파일을 어딘가에
올려 공개 주소를 만들어야 하고, 그러면 저장소라는 부품이 하나 는다.

**글 하나는 500자까지다.** 레시피는 그보다 길기 쉽다(실측 558~660자). 넘으면 통째로 거부되므로
나눠서 **글타래로 이어 단다.** 원본 작성자들이 하는 방식이다.

한도는 **450자로 잡는다.** 이모지·링크가 늘어나도 500 에 걸리지 않게 여유를 둔다.

**나누는 자리는 길이보다 절이 먼저다.** 준비물과 만드는 법은 길이가 남아도 갈라 서로 다른 답글로
올린다 — 읽는 사람이 재료를 보며 따라 할 수 있고, 한 조각이 길어져 엉뚱한 자리에서 잘리는 것도 막는다.
다만 제목 한 줄만 담긴 상태에서 끊으면 16자짜리 답글이 생기므로, 80자 미만 조각은 앞에 붙인다.

**준비물에는 재료마다 양을 적는다.** 원문에 적힌 분량을 그대로 옮기고, 원문에 없으면 이름만 적는다.
지어내지 않는다 — 따라 만드는 사람이 실패한다. 애초에 분량 표기가 3개 미만인 글은 후보에서 빠진다.

**대가성 문구는 링크와 한 문단으로 묶는다.** 공정위 지침상 필수인데, 문구와 링크 사이에 빈 줄을 두면
글타래가 나뉠 때 링크만 있고 고지가 없는 조각이 생긴다.

**막 올린 글에는 바로 답글을 못 단다.** 4279009(미디어를 찾을 수 없음)가 난다.
캐러셀·영상은 준비에 몇 초 걸리므로 그 오류에만 재시도를 건다.

**메타 CDN 영상은 Vercel Blob 으로 갈아 끼운다.** 저장소 `threads-media`(공개, iad1).
같은 이름이 있으면 업로드가 거부되므로 덮어쓰기를 켠다 — 이걸 놓쳐 영상이 통째로 빠진 적이 있다.

**미디어는 익을 때까지 기다려야 한다.** 스레드가 받아 처리하는 데 몇 초 걸리고,
덜 익은 채로 묶거나 내보내면 400 "슬라이드 하위 요소 오류" 가 난다.
`GET /{컨테이너}?fields=status` 가 `FINISHED` 가 될 때까지 기다린다.

### 점수 기준 — 문턱이 없으면 거꾸로 작동한다

표본 76개로 확인한 사실이다. **좋아요÷조회수만 쓰면 아무도 안 본 글이 1등을 한다.**

| 비율 | 좋아요 | 조회수 |
|---|---|---|
| 100% | 1 | 1 |
| 25% | 6 | 24 |

비율과 조회수의 상관계수가 **−0.177** 로 음수다. 많이 퍼질수록 비율은 떨어진다.
분모가 작으면 비율이 폭발하기 때문이다.

**그래서 문턱을 먼저 둔다.**

```
1차: 조회수 ≥ 5,000            — 실제로 퍼진 글만 남긴다 (표본 76개 중 20개)
2차: 좋아요 ÷ 조회수 로 등급
```

| 등급 | 비율 | 표본 분포 |
|---|---|---|
| 플래티넘 | ≥ 2.0% | 3개 |
| 골드 | ≥ 1.2% | 6개 |
| 실버 | ≥ 0.6% | 5개 |
| 브론즈 | < 0.6% | 6개 |

문턱값과 구간은 **설정으로 뺀다.** 표본 76개로 정한 값이라 더 모으면 조정할 수 있어야 한다.

### 요청 수를 줄이는 법

`reshare_count`(공유수)가 조회수와 상관계수 **0.606** 이고, **검색 결과에 이미 들어 있다.**
상세 요청은 무거우므로 공유수·좋아요로 1차 추린 뒤 상위 후보만 부른다.

## 3. 구조

우리가 운영하는 부품은 **크롬 확장 하나**다. 나머지는 부르기만 하는 외부 API다.

```
[크롬 확장]
   ├─(1) 수집   스레드 통신 가로채기 → 좋아요÷조회수 → 4등급 → 미디어 내려받기
   ├─(2) 제작   LLM → 본문 + 레시피 / 쿠팡 상품검색 → SubID 링크 → 레시피에 심기
   └─(3) 발행   스레드 공식 API → 본문 → 레시피를 답글로 이어붙임
```

외부 API 3종의 확인된 제약.

- **스레드 발행** — `graph.threads.net`. 컨테이너 생성 후 발행하는 2단계. 하루 250글·답글 1,000개.
  2026-08-18 에 앱 등록을 마쳤다. 계정 `example.cook`, 토큰 60일(만료 2026-10-17).
  받은 권한 — `threads_basic` · `threads_content_publish` · `threads_manage_replies` ·
  `threads_manage_insights` · `threads_read_replies`.
  **인사이트 권한이 딸려왔다** — 내가 올린 글의 조회수는 남의 글처럼 우회하지 않고 공식 API 로 읽는다.
- **스레드 키워드 검색 API 는 쓰지 않는다** — 심사 통과 전에는 내 글만 검색되고, 통과해도
  7일 500회 제한에 메타가 "경쟁사 모니터링 용도가 아니다"라고 명시한다. 그래서 수집은 인터셉터로 간다.
- **쿠팡** — 상품검색·딥링크·리포트. HMAC 서명이 필요한데 지금 코드는 Node 전용이라
  브라우저용(`crypto.subtle`)으로 이식해야 한다.

## 4. 위험과 격리

인터셉터와 미디어 재사용은 스레드 약관·저작권에서 위험 구간이다. 사용자가 위험을 인지하고 선택했다.

방어는 **격리**다. 위험한 것은 전부 `src/collect/` 안에만 둔다. 막히거나 방침이 바뀌면
그 폴더만 들어내고, 후보 글을 손으로 붙여넣는 방식으로 갈아탄다. 2·3단계는 그대로 산다.

웹스토어에 올리지 않고 압축을 푼 채로 직접 불러 쓴다. 그래서 "확장 삭제" 위험은 해당 없고,
남는 것은 계정 위험 하나다.

**옛 규칙 중 폐기하는 것** — `CLAUDE.md` 1번 "인터셉터 금지". 격리 규칙으로 대체한다.
**유지하는 것** — 값이 없으면 조용히 `null`. 틀린 숫자를 보여주느니 숨긴다.

## 9. 레시피 답글을 브라우저로 올린다 (2026-08-21)

### 9-0. 왜 하나

레시피 답글에 **쿠팡 링크가 들어가면 스레드가 미리보기 카드를 붙인다.** 공식 API 로는 못 끈다
(`link_attachment` 를 빈 값으로 줘도 붙는다 — 실측). 지금은 **링크가 든 조각에 본문 사진을
한 장 같이 보내서** 카드를 막고 있다 (`src/publish.mjs` 의 `붙일것`). 사진이 딸린 답글에는
카드가 안 붙기 때문이다.

그 대가로 **레시피 답글마다 본문에서 이미 본 사진이 한 번 더 붙는다.** 사용자가 이것을
없애고 싶어 한다. 카드도 사진도 없는 답글을 만들려면 API 로는 길이 없다.

### 9-1. 실측 — 브라우저로 무엇이 되는가 (2026-08-21)

Playwright 헤드리스로 실제 계정에서 확인했다. **추측이 아니다.**

| 확인한 것 | 결과 |
|---|---|
| `threads.com/t/{숫자 글번호}` 로 내 글 열기 | **안 된다.** 「페이지가 없습니다」 |
| `GET /v1.0/{글번호}?fields=permalink` | **된다.** `https://www.threads.com/@{계정}/post/{code}` 를 준다 |
| 글 페이지에 답글 칸 | **있다.** 글 바로 아래 인라인으로 있다 |
| 미리보기 카드 | **뜬다.** 단 「작성 도구 확장」을 눌러야 화면에 보인다 |
| 카드 지우기 | **된다.** 카드 오른쪽 위 X (`svg[aria-label="삭제"]`) |
| 조각 이어 달기 | **「스레드에 추가」**로 한 창에서 여러 조각을 쓴다 |
| 헤드리스 | **전부 된다.** 답글·메뉴 열기·글 삭제·카드 제거까지 창 없이 |

⚠️ **스레드 작성창은 엔터를 「게시」로 받는다.** `keyboard.type` 에 `\n` 이 섞이면
그 자리에서 글이 올라간다. **실제로 당했다** — 탐침 도중 첫 계정에 답글 한 개가 나갔고
1분 뒤 지웠다. 레시피는 여러 줄짜리라 이걸 모르면 반 토막 답글이 자동으로 계속 나간다.

**줄바꿈은 붙여넣기로 넣는다.** 키를 하나도 안 누르고 `paste` 사건만 보내면
빈 줄까지 그대로 살아난다 (실측).

```js
await 쪽.evaluate((글) => {
  const dt = new DataTransfer()
  dt.setData('text/plain', 글)
  document.activeElement.dispatchEvent(
    new ClipboardEvent('paste', { clipboardData: dt, bubbles: true, cancelable: true }))
}, 글)
```

### 9-2. 무엇이 바뀌고 무엇이 그대로인가

**본문은 그대로 공식 API 로 올린다.** 영상을 Blob 에 올리는 길, 미디어 익기 기다리기,
캐러셀 묶기가 전부 검증돼 있다. 브라우저로 옮기면 그것을 다 다시 짜야 하고 얻는 것이 없다.

**레시피 답글만 브라우저가 단다.** 그러면서 `붙일것`(링크 조각에 사진 붙이기)이 사라진다.

### 9-3. 순서

```
① 본문을 API 로 올린다                    → 본문번호
② API 에 그 글 주소를 묻는다               → permalink
③ 브라우저로 그 주소를 연다 (헤드리스, 계정 쿠키)
④ 답글 칸 → 조각1 붙여넣기
⑤ 「작성 도구 확장」 → 미리보기 카드가 있으면 X
⑥ 조각이 더 있으면 「스레드에 추가」 → 조각2 붙여넣기 → 카드 있으면 X
⑦ 「게시」
⑧ 글 페이지를 다시 읽어 조각들이 실제로 보이는지 확인한다
```

**⑧을 빼지 마라.** 단추를 눌렀다고 올라간 것이 아니다. 이 저장소는 "초록불인데 실제 경로는
죽어 있는" 사례를 반복해 겪었다. 화면을 다시 읽어 확인하는 단계가 완료의 증거다.

### 9-4. 되돌아갈 스위치

환경변수 `REPLY_VIA` 로 고른다.

**2026-08-21 부터 기본이 `browser` 다. 사용자가 정석으로 정했다.**
`api` 를 주면 옛 길(링크 조각에 사진을 붙여 카드를 막는 방식)로 물러선다.
스레드가 화면을 바꿔 선택자가 깨지는 날 그 한 줄로 즉시 되돌린다.

**이름을 영문으로 둔다 — bash 는 한글 변수명을 못 쓴다.** 시각표(`자동발행.sh`)가 넘겨야 하는 값이다.
**말썽이 나면 코드를 고치지 않고 한 줄만 바꿔 되돌린다.** 태그 `개편전-2026-08-21` 로
되돌리는 것보다 훨씬 빠르고, 계정별로 따로 켤 수 있다.

### 9-5. 어디에 켜나

처음에는 쟁여둔언니에만 켰다 (11:40). 실제 글로 확인한 뒤
**같은 날 사용자가 두 계정 모두, 그리고 앞으로 만들 계정까지 이 길을 정석으로 쓰기로 정했다.**
그래서 기본값이 `browser` 다. 새 계정은 아무것도 안 해도 이 길로 돈다.

### 9-6. 실패하면

본문이 올라간 뒤 답글이 실패하면 본문만 남는다. **지금 API 방식도 똑같다.**
숨기지 않고 기록에 적고 텔레그램으로 알린다. 알림이 실패해도 발행은 안 멈춘다.

브라우저가 아예 안 뜨거나 쿠키가 죽었으면 그때는 `api` 로 물러서지 않는다 —
조용히 다른 길로 새면 사진이 붙은 답글이 나가는데 아무도 모른다. **실패는 실패로 알린다.**

### 9-7. 답글 번호

브라우저는 글번호를 안 준다. 발행 뒤 `GET /me/threads` 로 최근 글을 받아 짝지어 얻는다.
없으면 없는 대로 둔다 — 본문 조회수와 답글 조회수를 견주는 데만 쓰는 값이라
그것 때문에 발행을 실패로 치지 않는다.

### 9-8. 검사

단추를 누르는 일이라 단위 검사로 못 덮는다. 세 겹으로 막는다.

- **붙여넣을 글에 엔터가 섞이지 않게 코드가 스스로 막는다** — 키보드로는 한 줄도 안 친다
- 조각 나누기·글자수 세기 같은 기존 로직은 검사 216개 그대로 유지
- **사람이 실제로 한 편 올려 눈으로 본다.** 이것이 진짜 검사다

## 10. 계정마다 분야 묶음을 하나씩 (2026-08-21)

### 10-0. 왜 하나

계정을 뷰티·패션·IT·캠핑으로 늘리기로 했다. 그런데 글 만드는 규칙이 요리 하나에
맞춰 통째로 박혀 있었다 — LLM 지시문, 쓸 만한 글인지 가리는 판정, 링크 심는 자리가 전부 요리용이다.
그대로 두고 분야만 켜면 **뷰티 글을 레시피로 다시 쓴다.**

### 10-1. 묶음이 정하는 것

`src/분야/{분야}.mjs` 한 파일이 그 분야의 전부다. `src/분야/고르기.mjs` 가 계정정보의
분야로 묶음을 찾아 준다. **기본값을 두지 않는다** — 묶음 없이 부르면 던진다.
기본값이 있으면 새 분야가 그것을 잊었을 때 조용히 요리 글이 나간다.

| 칸 | 하는 일 |
|---|---|
| `이름` · `글이름` | 화면과 지시문에서 부르는 말 (요리 = 레시피, 뷰티 = 사용법) |
| `쓸만한가(게시물)` | 후보로 쓸 글인가 |
| `결과검사(원문, 결과)` | LLM 이 망가뜨렸나. 없으면(`null`) 건너뛴다 |
| `링크앞머리` | 링크 문단을 어느 문단 앞에 끼울지 |
| `지시문` · `출력지시` · `부가글지시` · `규칙` | LLM 에게 줄 분야 전용 말 |
| `말투서식` | 새 계정을 만들 때 깔아 줄 말투 뼈대. 요리는 `null`(persona.json 을 쓴다) |

**수집·점수·중복 막기·미디어·발행·대시보드는 분야와 무관하다.** 그대로 둔다.

### 10-2. 옮길 때 확인한 것 — 초록불이 아니라 실제 값으로

요리를 묶음으로 옮기면서 나가는 글이 달라지면 안 된다. 셋을 다 쟀다.

| 무엇 | 결과 |
|---|---|
| `쓸만한가` | 실제 원글 214편에서 옛 판정과 다른 것 **0개** |
| `결과검사` | 실제 재구성 45쌍에서 다른 것 **0개** |
| LLM 지시문 | 실제 원글·말투로 만든 120쌍이 **한 글자도 안 다르다** |

⚠️ **지시문을 일반화하며 말을 다듬지 마라.** "재료" 를 "것" 으로 바꿨더니 120쌍이 전부 달라졌다.
분야가 정할 말은 전부 묶음으로 옮겨 **옛 글자 그대로** 둔다.

### 10-3. 뷰티 — 요리를 베끼면 안 되는 이유 (표본 60편, 실측)

| | 요리 | 뷰티 |
|---|---|---|
| 알맹이가 있는 곳 | 글타래 | **본문** — 60편 중 43편이 글타래가 없다 |
| 갈리는 신호 | 재료·분량·조리 동작 | **그 제품이 어떤가** (발림성·백탁·가성비) |
| 많이 섞이는 것 | 장보기 자랑·메뉴판 | **질문글**과 **판매자·시딩 글** |

**요리의 조리 동작에 해당하는 것을 찾다가 진짜 글 열둘을 막았다.**
선크림 글에 "바르다" 는 잘 안 나오고 "발림성·백탁·가성비" 가 나온다.
**뷰티의 알맹이는 바르는 순서가 아니라 그 제품이 어떤가다.**

지금 기준은 이렇다.

```
막는다  ① 추천해 달라고 조르는 글  ② 파는 사람·받은 사람의 글
        ③ 나쁘다고 말하는 글       ④ 남이 그러더라는 글
통과    제품 갈래가 잡히고 + (그 제품이 어떤지 말하거나 어떻게 쓰는지 말한다)
```

**"알려줘" 한 마디로 막으면 안 된다** — 제품을 제대로 평한 뒤 "다들 써봤어? 알려줘" 로
끝내는 글이 흔하고 그건 쓸 만한 글이다. **추천을 요청하는 말**만 막는다.

표본 60편에 손으로 표를 붙여 맞췄다 (통과 21 · 차단 39). 지금 양쪽 다 0편 틀린다.
**바꿀 때는 반드시 두 쪽을 다 재라.** 막아야 할 것이 막히는지, 그리고 진짜 글이 안 막히는지.

### 10-4. 새 분야를 여는 순서

```
① src/분야/{분야}.mjs 를 쓴다
② src/분야/고르기.mjs 의 묶음들에 등록한다
③ src/계정.mjs 분야들에서 됨: true 로 바꾸고 검색어를 채운다
```

셋을 다 해야 열린다. 하나만 하면 계정 만들기에서 막히거나 엉뚱한 분야 글이 나간다.

**검색어는 넓게 둔다.** 한 단어를 하루 몇 번만 두드려도 스레드가 그 단어를 조인다.
길이는 **24와 어긋나게** 잡는다 (요리·뷰티 모두 23) — 20이면 0시와 20시가 같은 자리를 집는다.

## 11. 조건을 팩으로 (2026-08-22)

### 11-0. 왜 하나

계정을 늘리고 해외로 나가려면 조건을 갈아 끼울 수 있어야 한다.
`계정정보.json` 에 **분야·언어·제휴** 세 칸이 이미 있었다. 그 셋을 그대로 팩으로 만든다.

```
src/언어/{언어}.mjs         광고 표기 · 그 언어로 쓰라는 지시 · 수량과 단위 규칙
src/분야/{분야}.mjs         판정 알고리즘 · 글 뼈대 · 지시문 조립  ← 언어와 무관하다. 한 벌뿐
src/분야/{분야}/{언어}.mjs   그 분야를 그 언어로 말하는 낱말과 문장  ← **데이터만. 함수 없음**
src/제휴/{제휴사}.mjs        상품 검색 · 링크 발급 · 대가성 문구
src/수량.mjs                분량이 원문과 같은지 견주는 알고리즘 한 벌
src/팩.mjs                  넷을 골라 **조립한다.** 없는 조합은 무엇이 없는지 말하고 막는다
```

**계정 하나 = 팩 셋의 조합이다.** 그 조합을 만들 때 분야팩만 「로직 + 낱말」로 한 번 더 조립한다
(11-1). 부르는 쪽(`run.mjs`·`compose.mjs`)은 조립된 것 하나를 받으므로 아무것도 모른다.

### 11-1. 분야팩은 왜 「로직 + 낱말」인가 (2026-08-26 에 다시 갈랐다)

재 보니 **판정 정규식 열넷이 전부 한국어 낱말**이었다 (실측 2026-08-22).

| 팩 | 한국어에 묶인 것 |
|---|---|
| 요리 | `먹는말`(소금·설탕·간장) · `만드는말`(볶·끓·굽) · `어림말`(약간·꼬집) · 단위(큰술·작은술) |
| 뷰티 | `제품말`(앰플·세럼) · `평가말`(발림성·백탁) · `물어보는말`(추천해줘) |
| 둘 다 | 검색어 23개 · 형식 라벨(`🛒 준비물`) · LLM 지시문 · 말투 뼈대 · 마법사 안내 |

**「大さじ2」는 한국어 요리팩의 수량꼴이 못 잡는다.** 한 파일에 두 언어를 담을 수 없다.
그래서 낱말은 `요리/한국어.mjs` 와 `요리/일본어.mjs` 로 갈려 있다.

**그런데 알고리즘까지 갈려 있었다.** 「이 글이 레시피인가」를 재는 코드가 요리 팩 셋에
**각각 베껴져** 있었고, 이런 베낌은 한쪽만 고쳐진다 — 수량 대조가 그렇게 사고를 냈다
(2026-08-24, §11-6). 그래서 2026-08-26 에 한 번 더 갈랐다.

| | 무엇을 갖나 | 몇 벌 |
|---|---|---|
| `분야/{분야}.mjs` | 판정 알고리즘 · 계정 잣대 · 지시문 조립 · 갖춰야 할 칸 목록 | 분야마다 **한 벌** |
| `분야/{분야}/{언어}.mjs` | 낱말(醤油·大さじ·발림성) · 지시문 문장 · 말투 서식 · 검색어 | 조합마다 하나 |

**「醤油」는 요리 낱말이면서 일본어 낱말이다.** 이 교차분은 어느 한쪽 팩으로도 못 옮긴다 —
없앨 수 없는 것을 **데이터로만** 남기고, 없앨 수 있는 것(알고리즘)만 한 곳에 모은 것이다.

낱말 파일이 언어마다 갖는 손잡이는 넷뿐이다.

| 손잡이 | 뜻 | 값 |
|---|---|---|
| `숫자최소` | 숫자 분량이 몇 개는 있어야 하나 | 한국어 3 · 일본어 2 · 영어 2 |
| `본문도본다` | 본문까지 읽나 | 영어만 참 (영어권은 레시피가 본문에 있다) |
| `지울꼴` | 분량으로 세면 안 되는 대목 | 영어의 영양 성분표만 |
| `촘촘단위꼴` | 조리 계량으로 치는 단위 | 언어마다 다름 |

**낱말 파일에 함수를 두면 안 된다.** 함수가 한 번 들어가면 알고리즘이 다시 언어별로 베껴진다.
`test.mjs` 가 낱말 파일의 모든 칸이 함수가 아닌지 본다.

### 11-2. 옮길 때 확인한 것

한국어 계정 둘이 지금과 똑같이 도는 것을 **실제 값으로** 확인하고 나서 일본어를 얹었다.

| 무엇 | 결과 |
|---|---|
| LLM 지시문 | 실제 원글·말투로 만든 120쌍이 **한 글자도 안 다르다** |
| 쓸만한가 | 실제 원글 232편에서 다른 것 **0개** |
| 링크 심기 | 글자 그대로 같다 |

### 11-3. 일본어 — 한국과 무엇이 같고 무엇이 다른가

표본 76편 실측 (글타래 있는 31편).

**같은 것** — 본문은 낚시, 材料·作り方 는 글타래. 아마존 링크와 `[PR]` 표기가 이미 널리 쓰인다.
`㊙️`·`秘密の材料`·`【リンクのこれ】` 처럼 **비밀재료 수법도 있다.**
⚠️ **2026-08-26 에 다시 재서 절반을 뒤집었다** (§11-7) — 제휴 계정에서는 실제로 쓰지만
일반 요리 글 108편에서는 0건으로 드물고, `隠し味` 는 **정체를 밝히는 말이라 별명이 아니다.**

**다른 것 둘. 이것을 모르면 진짜 레시피가 통째로 막힌다.**

⚠️ **일본어는 단위가 숫자 앞에 온다.** `大さじ1` 이지 `1大さじ` 가 아니다.
한국어처럼 숫자가 먼저인 꼴만 찾다가 **진짜 레시피 24편을 막았다.** 두 꼴을 다 훑는다.

⚠️ **일본 레시피는 어림말에 훨씬 많이 기댄다.** `少々`·`適量`·`たっぷり` 가 재료의 절반인
레시피가 흔하다. 숫자만 세면 막힌다. 어림말도 함께 세되 **숫자 분량이 둘은 있어야 한다** —
어림말만 늘어놓은 글은 따라 만들 수가 없다.

표 붙인 31편에서 지금 양쪽 다 0편 틀린다. 글타래 없는 45편도 하나도 안 샌다.
한국어 글은 일본어 팩을 통과하지 못한다.

### 11-4. 제휴 「없음」도 팩이다

링크·광고 표기·대가성 문구를 **셋 다 안 붙인다.**
해외 계정은 아마존 어소시에이트 승인 전까지 이 상태로 돈다 — 계정만 키운다.
**광고가 아닌 글에 광고 표기를 붙이는 것도 거짓말이다.**

⚠️ **해외 = 수익이 바로 되지 않는다.** 아마존은 나라별로 따로 가입·심사해야 하고,
가입 후 180일 안에 판매 실적이 없으면 계정을 닫는다. 상품 API 는 실적이 생겨야 열어 준다.

### 11-7. 언어팩은 한국어팩을 기준으로 견준다 (2026-08-26 — 사용자가 정한 규칙)

**한국어팩이 기준이다.** 한국어팩이 다루는 것은 다른 언어팩에서도 **반드시 판단해야 한다.**
「그 언어에는 그런 게 없겠지」 하고 건너뛰면 그 계정만 조용히 반쪽이 된다.

판단은 셋 중 하나로 끝난다.

| 판단 | 무엇을 하나 |
|---|---|
| 그 언어에도 있다 | **그 언어 사용자가 실제로 쓰는 말**을 재서 적는다. 번역하지 않는다 |
| 있는데 말이 다르다 | 실제 말로 바꿔 적고, 왜 다른지 근거를 함께 적는다 |
| 그 언어에는 없다 | **없다는 것도 실측으로 적는다.** 빈칸으로 두지 않는다 |

**번역은 근거가 아니다.** 「킥소스」를 사전으로 옮기면 `キックソース` 가 나오는데 아무도 안 쓴다.
스레드에서 실제로 걷어 세어 봐야 한다 (`검색()` 은 쿠키 없이도 돈다).

#### 이 규칙이 나온 자리 — 비밀재료

한국어 요리팩에는 「비밀재료」(정체를 감춘 별명 재료)를 다루는 지시와 그물이 있었다.
다른 언어를 재 보니 **양쪽으로 어긋나 있었다.**

| | 한국어 | 일본어 | 영어 |
|---|---|---|---|
| LLM 에게 채우라는 지시 | ✅ | ❌ 없었다 | ❌ 없었다 |
| 별명 그물(`별명꼴`) | ❌ `compose.mjs` 에 박혀 있었다 | ✅ | ✅ |

JSON 칸은 언어와 상관없이 늘 `비밀재료`·`한줄소개` 를 요구하는데 **채우는 법을 안 알려 줬고**,
그물은 거꾸로 한국어 것이 코드에 박혀 있어 **일본어·영어 계정에는 그 안전장치가 아예 없었다.**

#### 실측 결과 — 언어마다 다른 말을 쓴다

2026-08-26, 각 언어 요리 검색어 23개로 걷어 그 언어 요리 글만 골라 셌다.

| | 표본 | 재료를 별명으로 감추나 | 실제로 쓰는 감추기 |
|---|---|---|---|
| 한국어 | 요리 글 113편 | **있다** — 「비법가루가 있답니당」 | 레시피·링크를 댓글·DM·프로필로 |
| 일본어 | 요리 글 108편 | 일반 글에는 **0건** (제휴 계정에는 있다) | `レシピはコメント欄` · `プロフィールをチェック` · `Instagramのハイライト` |
| 영어 | 요리 글 127편 | 자연 표본 **0건**, 낱말로 찾으면 있다 (`* 5–6 tbsp secret ingredient`) | `Recipe in comments below` |
| 뷰티(한국어) | 뷰티 글 181편 | **아니다** — 별명이 아니라 아예 안 적는다 (「제품명은 댓글에 이어서」) | 프로필 링크 · 고정 댓글 |

**세 언어 모두 주류는 「딴 데로 보내기」다.** 그건 별명이 아니라 **글에 레시피가 없는 것**이라
`쓸만한가` 가 이미 막는다. 별명 그물이 다룰 일이 아니다.

#### 언어팩이 죽어 있었다

`쓰기지시`(「日本語で書く。韓国語や英語を混ぜない。」)가 **아무 데서도 안 쓰이고 있었다.**
언어를 붙들고 있던 것은 계정 말투 파일(`persona.<계정>.json` 의 `지켜야 할 것`)이었다 —
계정을 만들 때 말투서식에서 복사된 줄이다. **말투는 사람이 고치는 것이라 지워질 수 있다.**

`src/언어규칙.mjs` 를 두고 분야 로직(요리·뷰티)이 **규칙 칸 맨 앞에** 언어팩 지시를 박게 했다.
`compose.mjs` 는 안 고쳤다 — 팩이 조립될 때 이미 들어가 있다.

#### 가장 위험했던 것 — 뜻이 뒤집히는 말

일본어 그물에 `隠し味` 가 들어 있었다. 그런데 **일본어 `隠し味` 는 정체를 밝히면서 쓰는 말이다** —
걷은 12줄이 전부 「隠し味は「ナンプラー」と「ライム」。」 「隠し味教えてください」 였다.
그물에 두면 **정체를 밝힌 진짜 재료 줄을 지운다.** 걷어냈다.

`シークレット` 단독도 뺐다 — 요리와 무관했다 (아이돌 굿즈·드라마 10줄).
거꾸로 **인계에 실측으로 적혀 있던 `秘密の材料`·`【リンクのこれ】` 는 그물이 못 잡고 있어** 넣었다.

**남의 언어 낱말을 뜻만 보고 넣지 마라. 그 말이 반대 뜻으로 더 많이 쓰이는지 세어 봐라.**

### 11-5. 새 팩을 넣는 순서

```
① 낱말 파일을 만든다  ② src/팩.mjs 목록에 등록한다  ③ src/계정.mjs 에서 됨: true 로 바꾼다
```

**있는 분야에 언어를 더할 때는 ①이 낱말 파일 하나로 끝난다** (알고리즘을 안 건드린다).
새 분야를 열 때만 `분야/{분야}.mjs` 로직도 함께 쓴다 — 요리와 뷰티는 판정이 아예 달라서
억지로 한 로직에 묶지 않았다.

셋을 다 해야 열린다. **분야와 언어를 따로 보면 안 된다** —
「요리도 되고 일본어도 되는데 요리 × 일본어 팩은 없다」가 생긴다.
화면은 `되는조합()` 으로 함께 본다.
