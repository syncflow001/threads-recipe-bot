## 믿었던 것
본 크롬 쿠키 읽기를 처음 붙이고 돌렸더니 「로그인된 프로필 0개」가 나왔다.
바로 앞 판에서 프로필 열셋에 `sessionid` 가 다 있는 것을 눈으로 봤는데도,
그 0을 「복호화가 틀렸나 보다」로 읽었다. 실제로는 **복호화까지 가지도 못했다.**

## 해본 것
읽는 함수 `프로필쿠키()` 가 통째로 `try { … } catch { return null }` 이었다.
catch 를 걷어내고 한 프로필만 손으로 돌려 진짜 오류를 받아 봤다 (2026-09-08).

## 나온 것
```
RangeError: Value is too large to be represented as a JavaScript number: 13462001090256144
```
쿼리 자체가 던지고 있었다. 크롬의 `expires_utc` 는 **1601년부터 잰 마이크로초**라
자바스크립트가 정확히 담는 한계(9,007,199,254,740,991)를 넘고, `node:sqlite` 는
값을 뭉개는 대신 던진다. 복호화는 처음부터 멀쩡했다 — SQL 에서 `expires_utc/1000000` 로
초로 줄여 받자 프로필 13곳이 전부 나왔고, 그중 12개가 우리 계정이었다.
(`src/크롬쿠키.mjs` · `검사/test.크롬쿠키.mjs` ④ · 커밋 `a067512`)

## 지금 결론
**「0개」를 결과로 읽기 전에 그 0이 어디서 왔는지 본다.** 던진 것과 진짜 없는 것은
화면에서 똑같이 0이다. 넓은 `catch` 로 `null` 을 돌려주는 자리는 그 둘을 뭉갠다 —
읽기 실패는 빈손이 아니라 **까닭**을 줘야 한다. `크롬쿠키들()` 은 이제 크롬 폴더가 없으면
`크롬없음` 을 던지고, 검사가 그것을 지킨다.
같은 결의 카드 — [[없는-계정과-빈-계정은-다르다]] · [[못-읽는-것과-없는-것을-가르려면-남의-눈으로-같은-것을-봐라]].

## 아직 모르는 것
`프로필쿠키()` 안에는 아직 `catch { return null }` 이 남아 있다 (프로필 하나가 깨져도
나머지는 읽어야 하기 때문이다). 그 자리에서 무엇이 얼마나 자주 삼켜지는지는 안 재 봤다.
크롬이 저장 방식을 또 바꾸면 여기가 먼저, 그리고 조용히 깨진다.
