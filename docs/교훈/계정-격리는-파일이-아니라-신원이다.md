## 믿었던 것

계정마다 폴더를 나누고 경로를 한 곳으로 모으면 **「한 판이 도는 동안 남의 계정을 침범하지
않는다」가 끝난다**고 봤다.

## 해본 것

「정말 다 격리됐나」를 갈래마다 실측했다 — 토큰·쿠키·길들이기·수집·하트댓글·발행·
보관함·재구성·모니터링.

## 나온 것

**파일은 다 갈렸는데 두 곳이 뚫려 있었다.** 둘 다 폴더와 무관했다.

| 뚫린 곳 | 무슨 일 |
|---|---|
| 브라우저 | `sample_table` 이 `sample_minimi` 쿠키로 **여덟 판 동안 남의 홈을 영어 요리 글로 길들였다.** 같은 홈에서 글 43편도 걷었다 |
| 토큰 | 열쇠 파일에 남의 토큰이 들어가면 스레드 API 가 **그 계정으로 글을 올린다.** 벽이 아예 없었다 |

증거가 딱 맞았다 — 길들이기 장부에 「목표언어 영어」인데 **걷은 글의 한국어 비율이 88%** 였다.

곁가지로 계정 번호 캐시가 모듈에 하나뿐이라, 한 프로세스에서 두 계정을 다루면
**먼저 물어본 번호가 뒤 계정에도 쓰였다**(실측 — B 토큰에 A 번호가 나왔다).

## 지금 결론

**섞이는 것은 파일이 아니라 신원이다.** 폴더는 「내 것을 어디 두나」를 풀지, 「지금 이
브라우저·이 토큰이 누구냐」를 풀지 않는다. 문이 셋 필요하다.

| 문 | 언제 묻나 |
|---|---|
| 파일 | 경로를 만들 때 (`계정길()` 하나) |
| 토큰 | API 로 글 올리기 직전 (`토큰벽()`) |
| 브라우저 | 크롬 열기 **전** (`계정이름으로벽()`) |

브라우저 벽은 **열기 전**이어야 한다. 열고 나면 그 자체가 그 계정으로 접속한 흔적이다.

**벽을 자리마다 손으로 붙이지 않는다.** 그게 구멍이 생긴 이유다. 「쿠키를 브라우저에
심는 파일은 반드시 벽도 부른다」를 소스 검사로 못 박았다. `홈에서걷기()` 가 길들이기와
수집이 함께 쓰는 유일한 문이라 거기 하나만 지켜 둘 다 지켰다.

셋 다 **주인을 못 읽으면 안 막는다.** 벽이 모든 활동을 세우면 사고를 막는 게 아니라
프로그램을 죽이는 것이다.

## 아직 모르는 것

- 실제로 글을 올려서 토큰벽을 확인하지는 못했다. 가짜 응답으로만 쟀다
- 벽은 「열쇠가 어긋난 것」을 잡는다. 스레드가 계정을 제재하는 것은 여전히 사후에 안다
