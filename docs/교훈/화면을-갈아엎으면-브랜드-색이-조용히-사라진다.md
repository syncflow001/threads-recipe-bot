## 믿었던 것

대시보드를 새 틀(Next + shadcn)로 옮기면서 `design-system/브랜드.md` 는 그대로 뒀으니
색도 그대로 따라왔다고 봤다. 문서가 살아 있으니 지킨 셈이라고 여겼다.

## 해본 것

옮긴 뒤 여러 세션 동안 아무도 못 알아챘다.
사용자가 화면을 보고 말했다 — 「대시보드 색상이 아예 없어진 게 아쉽네」.

## 나온 것

`dashboard/app/globals.css` 가 **shadcn 기본값 그대로**였다.
모든 색이 `oklch(... 0 0)` — 채도가 0, 즉 회색뿐이다.

브랜드 문서 §3 에는 색이 멀쩡히 적혀 있었다 (바탕 `#eef3f0` · 으뜸 `#2f9e74` · 글 `#1f2a37`).
**옮긴 사람이 없었을 뿐이다.** 문서 첫머리의 「색을 고칠 때는 이 파일과 `:root` 를 함께 고친다」는
안내도 옛 파일(`src/설정화면-html.mjs`)을 가리키고 있어서, 새 파일로 옮겨질 때 아무도 안 따라갔다.

차트만은 멀쩡했다 — `실적그림.tsx` 가 `#2f9e74` 를 **코드 안에 직접 박아** 뒀기 때문이다.
변수를 쓴 곳은 다 회색이 됐고, 박아 둔 곳만 살아남았다.

## 지금 결론

**화면 틀을 갈 때는 「무엇을 옮겼나」가 아니라 「무엇이 안 따라왔나」를 센다.**
브랜드 색·글꼴은 문서에 있다고 반영된 것이 아니다 — 새 파일의 `:root` 를 열어 눈으로 본다.
`docs/문서점검` 은 문서끼리만 보므로 이런 문서↔코드 어긋남을 못 잡는다
(2026-08-28 지식축적 세션 알게 된 것 6번이 이미 짚었다. 이번이 그 「한 번 더」다).

되돌린 것은 커밋 `b07bce6` 이다. 브랜드 문서의 「함께 고친다」 대상도 새 파일로 고쳐 적어야 한다.

## 아직 모르는 것

글꼴은 아직 안 봤다. 브랜드 §4 는 본문 시스템 기본 · 숫자 고정폭이라 적었는데
새 틀이 그대로인지 확인 안 했다. 색 말고 또 무엇이 안 따라왔는지도 다 세지 않았다.
