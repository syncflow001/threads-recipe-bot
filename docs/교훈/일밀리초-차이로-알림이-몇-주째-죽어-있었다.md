## 믿었던 것

「텔레그램이 이 맥에서 안 나간다」를 **알 수 없는 그물 문제**로 몇 주 두었다.
`fetch failed ETIMEDOUT` 인데 `curl` 은 302 를 잘 받아서, 방화벽이나 텔레그램 쪽 차단이라 짐작했다.
IPv4 를 강제해 봤는데 「안 되더라」로 적어 두고 넘어갔다.

## 해본 것

섀도우밴 알림을 붙이고 나서 **내가 만든 알림이 사용자에게 못 간다**는 것을 깨닫고 다시 팠다.
짐작을 걷어내고 층마다 잰다.

## 나온 것

| 무엇 | 결과 |
|---|---|
| DNS | IPv4 `149.154.166.110` · IPv6 `2001:67c:...` 둘 다 나온다 |
| 생 TCP → IPv4 | **251ms 에 붙는다** |
| 생 TCP → IPv6 | `EHOSTUNREACH` 3ms (경로가 아예 없다) |
| TLS `family: 4` | 506ms 성공 |
| TLS 기본(가족 지정 없음) | **ETIMEDOUT 257ms** |
| `curl` | 302, 0.78초 |

Node 는 주소가 둘이면 먼저 것을 **250ms** 안에 못 붙으면 포기하고 다음으로 넘어간다
(Happy Eyeballs · `autoSelectFamilyAttemptTimeout` 기본값).
이 맥의 IPv4 연결이 **251ms**다. **1ms 차이로** IPv4 를 버리고 경로가 없는 IPv6 로 넘어가 죽는다.

`net.setDefaultAutoSelectFamilyAttemptTimeout(1000)` 한 줄로 그 자리에서 살아났다 —
`fetch` 200, 알림 `{보냄: true}`.

## 지금 결론

**`fetch` 는 실패하는데 `curl` 은 되면 Node 의 IPv6 헛디딤을 먼저 의심한다.**
쉽게 재는 법 — `net.connect` 로 IPv4·IPv6 각각 붙여 보고 걸리는 시간을 잰다.
IPv4 가 250ms 언저리이고 IPv6 가 `EHOSTUNREACH` 면 그것이다.

`src/그물.mjs` 를 만들어 불러 쓰기만 하면 문턱이 올라가게 했다.
**검사(`test.그물.mjs`)가 값을 했다** — 처음에 여섯 모듈(`알림`·`threads`·`publish`·`coupang`·
`화면엔진`·`설정화면-터미널`)만 손댔는데, 검사가 **여섯을 더 찾아냈다**
(`media`·`도달`·`성적`·`업데이트`·`토큰받기`·`팔로워`). 손으로 셌으면 절반을 놓쳤다.

## 아직 모르는 것

왜 이 맥의 IPv4 연결이 하필 251ms 인지는 모른다. 인터넷이 빨라지면 문제가 저절로 사라지고,
느려지면 다른 주소에서도 같은 일이 난다 — 그래서 문턱을 1초로 넉넉히 잡았다.

「IPv4 강제도 안 되더라」던 옛 기록이 왜 그랬는지는 모른다. 지금은 `family: 4` 가 잘 된다.
그때 잰 방법이 달랐을 것이다 — **「해봤는데 안 되더라」를 근거로 남기면 안 된다는 뜻이기도 하다.**
